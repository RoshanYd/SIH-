Design Document for SIH26017

Yes. Below is the **master UI/UX + product specification** I would use as the source of truth for the frontend team/AI coding agent.

The central constraint is:

> **Design against the real land-acquisition lifecycle and the real fields we expect from government sources—not against synthetic/demo data.**

The demo dataset can populate the UI now, but **the UI's information architecture, terminology, workflows, filters, forms, tables, and data contracts should already resemble the eventual real system.**

> **Early Warning & Decision Support**

Alternative internal name:

# 2. The problem we're solving

Large infrastructure projects depend on timely land acquisition.

An officer may have information scattered across:

* land acquisition records
* statutory notifications
* litigation information
* compensation records
* environmental clearances
* geographical information
* district-level information
* project progress

The problem isn't simply lack of data.

The problem is:

> **The officer cannot easily see the complete current state of acquisition, identify emerging bottlenecks, prioritize projects, and intervene early.**

Therefore the system must transform fragmented information into:

**Situation → Risk → Explanation → Priority → Action → Monitoring**

---

# 3. Primary users

Design primarily for three levels.

### Level 1 — District/CALA Officer

Needs:

* individual project status
* acquisition stage
* pending issues
* litigation
* compensation
* clearances
* immediate actions

### Level 2 — State/Regional Officer

Needs:

* projects across districts
* district comparisons
* risk concentration
* bottleneck trends
* agency performance

### Level 3 — Senior/Department Officer

Needs:

* overall portfolio health
* critical projects
* emerging risks
* delay trends
* intervention outcomes

**The UI should adapt information density, not create completely different applications.**

# 5. Golden UX rule

### Never make the officer interpret ML output.

Bad:

> Model probability: 0.83

Good:

> **High delay risk**

Then:

> Estimated additional delay: **180–240 days**

Then:

> **Primary concern: Litigation**

Then:

> 14 active project cases
> 1 stay order
> 7 arbitration petitions

Then:

> **Review litigation affecting pending parcels**

The AI is behind the interface.

The officer sees the decision.

# 8. Visual design language

The visual direction should combine:

### Apple

* whitespace
* typography
* hierarchy
* restrained colors
* subtle shadows
* minimal visual noise

### Monday.com

* information-dense tables
* filters
* status chips
* interactive boards
* quick actions
* clear project states

### Government enterprise software

* reliability
* clarity
* accessibility
* predictable navigation
* explicit status
* auditability

Do **not** make it look like a flashy startup AI dashboard.

No:

* excessive gradients
* glowing cards
* giant AI illustrations
* neon colors
* excessive animations
* unnecessary 3D graphics

Your dataset's district-level features are therefore not just ML variables.

# 35. Observed vs predicted

This is an essential design principle.

Every insight should fall into one of three categories:

### Observed

Directly from government/project data.

```text
3G date: 15 Dec 2024
```

### Derived

Calculated from observed data.

```text
Days since 3G: 286
```

### Predicted

Produced by ML/model.

```text
Delay risk: High
```

The UI should make this distinction clear.

# 53. IMPORTANT: Don't put target leakage fields into the live prediction interface

This matters for your ML architecture.

For example:

```text
Actual_Completion_Date
Delay_Days
Is_Delayed_90D
Is_Delayed_180D
Is_Delayed_365D
```

are **outcomes**.

They should not be used as inputs to predict future delay.

In the UI they belong under:

> **Historical / Outcome**

or:

> **Performance**

not:

> Current risk factors.
